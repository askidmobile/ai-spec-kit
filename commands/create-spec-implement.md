# Реализатор плана по фазам (IMPLEMENT)

Ты — старший инженер. Твоя задача — реализовать одну фазу плана: **$ARGUMENTS**

> **Реализация = одна фаза за раз. Написать код, проверить, зафиксировать.**
> Входные данные — утверждённый план из `docs/plans/`.

---

## ФАЗА 1: Разведка (МОЛЧА, без вывода)

### 1.1. Найти план

Если `$ARGUMENTS` содержит путь к файлу → прочитай его.
Если `$ARGUMENTS` — название → найди:
```
Glob: docs/plans/*$ARGUMENTS*
```
Если не найден → покажи список: `ls docs/plans/` и предложи `/create-spec-plan <название>`.

### 1.2. Определить прогресс

Прочитай план целиком. Для каждой фазы определи статус:
- ✅ **Завершена** — все `[x]` в чеклисте
- 🔄 **В процессе** — часть `[x]`, часть `[ ]`
- ⬜ **Не начата** — все `[ ]`

### 1.3. Найти связанную спеку

Прочитай поле `**Спецификация:**` в плане → загрузи связанную спеку из `docs/specs/`.

### 1.4. Проверка незакрытых вопросов

Прочитай в плане секцию «Отложенные вопросы», в спеке — то же самое. Для каждой записи:

- Если `Когда нужен ответ` указывает на ТЕКУЩУЮ фазу плана или раньше → этот вопрос **блокирует** реализацию. Добавь в очередь.
- Если запись касается фазы, которая НЕ выбрана сейчас — пропусти, разберёшься в следующем вызове `/create-spec-implement` для той фазы.

Если очередь не пуста — задай вопросы **по одному** через `AskUserQuestion` (см. [правила интерактивных вопросов](#правила-интерактивных-вопросов-общий-блок)). После каждого ответа:

1. Открой файл-источник (план или спека) и перенеси запись из «Отложенные» в «Решения по плану» / «Решения по спеке».
2. Если ответ меняет задачи фазы — обнови чеклист фазы в плане.

Не переходи к Фазе 2, пока очередь не пуста.

## ФАЗА 2: Выбор фазы

Покажи пользователю **одним сообщением**:

```
📋 План: [Название плана]
📄 Спека: [путь к спеке]

Прогресс фаз:
  ✅ Фаза 1: [Название] — завершена
  🔄 Фаза 2: [Название] — в процессе (3/5 задач)
  ⬜ Фаза 3: [Название] — не начата
  ⬜ Фаза 4: [Название] — не начата

→ Предлагаю: Фаза N — [Название] (оценка: X ч)
  Задачи:
  - [ ] Задача 1
  - [ ] Задача 2
  - ...
```

Если пользователь указал номер фазы в `$ARGUMENTS` → предложи именно её.
Иначе → предложи следующую незавершённую (первую ⬜ или 🔄).

**НЕ ПЕРЕХОДИ ДАЛЬШЕ, пока пользователь не подтвердит фазу.**

## ФАЗА 3: Загрузка контекста (МОЛЧА, без вывода)

После подтверждения фазы:

### 3.1. Файлы фазы
Прочитай ВСЕ файлы, перечисленные в задачах выбранной фазы (пути из чеклиста `→ path/to/file`).

### 3.2. Связанные требования
Найди в таблице "Трейсабельность: Требования → Задачи" какие FR-XXX покрывает эта фаза.
Прочитай эти требования в спеке.

### 3.3. Паттерны проекта
Изучи аналогичные реализации в кодовой базе — как устроены похожие модули, обработка ошибок, тесты.

Покажи пользователю **одним сообщением** план атаки:

```
🎯 Фаза N: [Название]

Покрывает требования: FR-001, FR-002, ...

Валидация после реализации:

```

**НЕ ПЕРЕХОДИ ДАЛЬШЕ, пока пользователь не подтвердит план атаки.**

## ФАЗА 5: Реализация

Выполняй задачи фазы **строго по порядку**.

### Правила реализации:

1. **Одна задача за раз** — закончи текущую, потом переходи к следующей
2. **Следуй паттернам проекта** — не изобретай свою архитектуру, копируй стиль из аналогичных модулей
3. **Мини-проверка после каждой задачи** — если задача модифицирует Rust-код → `cargo check` после неё. Если TypeScript → `tsc --noEmit`. Если добавляет тест → запусти его
4. **Проблемы → сообщай сразу** — если задача невозможна или требует изменения плана, останови реализацию и сообщи пользователю
5. **Не выходи за scope фазы** — не делай задачи из других фаз, не "улучшай" код вне плана
6. **Неоднозначность → задай через `AskUserQuestion`**. Если по ходу реализации появилась развилка, которая не покрыта планом/спекой (выбор API, форма данных, текст ошибки, поведение в граничном кейсе) — **не угадывай**. Задай вопрос по правилам общего блока, дождись ответа, зафиксируй решение в плане (секция «Решения по плану», `PD-NNN`) и только потом продолжай.

## Правила интерактивных вопросов (общий блок)

При закрытии вопросов через `AskUserQuestion`:

- **Один вопрос = один tool call** (массив `questions` длины 1).
- **2-4 варианта** + автоматический Other.
- **Контекст в вопросе**: 1-2 предложения почему спрашиваешь и как ответ влияет на текущую задачу.
- **Label короткий** (1-5 слов), **description** объясняет последствия.
- **Рекомендация** — первой опцией с `(Рекомендуется)`, если есть обоснованная.
- **header** — 1-3 слова, чип-метка темы.
- **После ответа** — обнови файл плана/спеки (записать в «Решения»), потом продолжай реализацию.

### После каждой задачи (кратко):
```
✅ Задача N: [описание] — готово
   Файлы: path/to/file (+XX/-YY строк)
```

## ФАЗА 6: Валидация

После завершения всех задач фазы выполни полную валидацию:

### 6.1. Компиляция
- Rust: `cargo check` (весь проект)
- TypeScript: `tsc --noEmit`
- Другой стек: адаптируй под проект

### 6.2. Тесты
- Запусти тесты, связанные с изменёнными модулями
- Если фаза включала написание тестов — запусти их отдельно

### 6.3. Линтинг (если настроен)
- `cargo clippy`, `eslint`, `prettier` — то что настроено в проекте

### Результат валидации:
```
🔍 Валидация Фазы N:
  ✅ Компиляция — OK
  ✅ Тесты — 12 passed, 0 failed
  ⚠️ Clippy — 1 warning (не критично)
```

Если валидация провалилась → исправь ошибки и повтори валидацию.

---

## ФАЗА 7: Фиксация

### 7.1. Обновить план
Открой файл плана и отметь выполненные задачи: `[ ]` → `[x]`

### 7.2. Обновить TASKS.md (если есть)
Если задача зарегистрирована в TASKS.md — обнови прогресс.

### 7.3. Предложить коммит
Предложи пользователю сделать коммит с описанием:
```
Предлагаю коммит:
  feat(<модуль>): <краткое описание фазы> (T-XXX)

  Фаза N из M плана [название]:
  - [Что реализовано — по задачам]
```

### 7.4. Финальный вывод

```
📊 Фаза N завершена!

Реализовано задач: X/X
Файлов изменено: Y
Валидация: ✅ OK

Прогресс плана:
  ✅ Фаза 1: [Название]
  ✅ Фаза 2: [Название]  ← текущая
  ⬜ Фаза 3: [Название]
  ⬜ Фаза 4: [Название]

→ Следующий шаг: /create-spec-implement <путь-к-плану> фаза N+1
```

Если это была последняя фаза:
```
🎉 Все фазы плана реализованы!

→ Следующий шаг: /create-spec-review <путь-к-плану>
```
